# Character Reverse Seed Search — Algorithm & Rationale

The character Reverse Seed Search (RSS) recovers Melee's 32-bit RNG seed from a
short sequence of observed random-character selections. The canonical implementation
is a **direct truncated-LCG / Hidden-Number-Problem (HNP) reconstruction** via a
Babai closest-vector (CVP) solve — implemented in [`charrss.py`](charrss.py)
([`cvp_basis`](charrss.py#L114)/[`cvp_prepare`](charrss.py#L146)/[`cvp_search`](charrss.py#L165)), baked by [`tools/gen_charrss_constants.py`](tools/gen_charrss_constants.py),
and ported to the browser runtime [`docs/js/charrss.js`](docs/js/charrss.js).

**At 9 characters** the search recovers the exact seed with 100% success and no
brute-force residual, in ~0.26 ms. Validated: JS 5000/5000 exact, 0 false positives;
JS≡Python cross-impl; 4000/4000 agreement with `rng.cpp locateCharSequence_` (via
`api.findSeed`).

---

## 1. The underlying problem: truncated-LCG reconstruction

What we have:

- The seed advances by an affine map; character `k` is read from seed
  `sₖ = aₖ·u + bₖ (mod 2³²)` where `u` is the anchor seed and `aₖ = A²ᵏ` (two LCG steps/char).
- `rand_int(sₖ,25) = ((sₖ>>16)·25)>>16` tells us **which of 25 contiguous intervals `sₖ` falls
  in** — i.e. it leaks the _high_ bits of `sₖ`. Each character pins `sₖ` to a known window
  `[Lₖ,Uₖ]` of width ≈ 2³²/25 ≈ 1.717e8 (the `CHAR_RANGES` table).

"Recover the full LCG state from several high-bit-truncated outputs" is exactly the classic
**truncated-LCG / Hidden Number Problem (HNP)** that the literature (Frieze–Håstad–Kannan–
Lagarias–Shamir; Stern; Boneh–Venkatesan) solves with **a single lattice closest-vector
computation** — no skipping, no `Σ|c|<25` budget constraint at all.

Information budget: each character leaks `log₂25 ≈ 4.64` bits. The seed is 32 bits.

```
9 chars → 41.8 bits   (≈ 9.8 bits of margin over 32 — comfortable)
8 chars → 37.1 bits   (≈ 5.1 bits margin — near the edge)
7 chars → 32.5 bits   (essentially the uniqueness cliff)
```

So 9 characters is _over-determined_ for direct reconstruction. The only question is whether a
**polynomial-time, single-shot** lattice solve realizes that margin in practice. It does.

## 2. The algorithm: direct Babai CVP reconstruction

We know `aₖ·u + bₖ` lies in `[Lₖ,Uₖ]`; let `cₖ` be each interval's center and
`targetₖ = (cₖ − bₖ) mod 2³²`. We want `u` such that `aₖ·u (mod 2³²)` is within a half-interval
(`≈ 2³²/50`) of every `targetₖ`. Cast as a closest-vector problem:

- Lattice basis `G` (rank `n`):
  - row 0 = `(a₀, a₁, …, a_{n−1})` — the coefficient of `u`;
  - rows 1…n−1 = `2³²·eₖ` — the modular-wrap directions.
- LLL-reduce `G` (depends only on the **sequence length**, so it is precomputed **once** and
  baked offline).
- Babai nearest-plane to `target = (target₀,…,target_{n−1})`; read `u` off coordinate 0;
  verify by regenerating the characters.

`u` is determined mod 2³², so coordinate 0 of the closest lattice point _is_ the anchor seed.
The lattice dimension is ~9–10 — Babai there is microseconds.

### 2.1 Measured results (original single-Babai probe)

Random seeds, characters generated by the same `generate_chars` oracle the project already uses;
`window=0` means **pure Babai with no brute-force residual at all**:

```
chars= 8  window=±0       191/200 solved   0.20 ms/seed
chars= 9  window=±0      5000/5000 solved  0.26 ms/seed     ← target
chars=10  window=±0      5000/5000 solved  0.31 ms/seed
chars=11  window=±0       200/200 solved   0.38 ms/seed
chars=13  window=±0       200/200 solved   0.52 ms/seed
```

**At 9 characters the direct CVP recovers the exact seed every time with no residual scan**, in
about a quarter of a millisecond — versus the old server brute force, which scans ~171.8M seeds.
At 8 characters it already succeeds ~95.5%

The result: **9 characters (the uniqueness minimum), no brute-force residual, a small baked
table, and a fast lattice.**

## 3. Robustness and the hybrid safety net

The clean way to ship this keeps a tiny, bounded fallback so it is never worse than today:

- **Residual verify (always).** Babai returns one candidate `u`; regenerate the 9 characters and
  accept only on exact match.
- **Short enumeration (cheap insurance).** If the exact-match check fails (should never happen at 9 chars), enumerate the few closest lattice vectors
  (Babai → Kannan/Fincke–Pohst enumeration of radius ~1.5·error) and test each. Dimension ~10
  enumeration of a handful of candidates is still sub-millisecond. This is the principled version
  of the `±window` brute scan in the probe.
- **"Enter one more character" fallback.** Identical to the current multi-match UX. Empirically
  unnecessary at 9; available for free if a pathological seed ever appears.

So the production recipe is **CVP → 1-seed verify → (fallback) tiny enumeration**, with a hard upper
bound on work measured in microseconds, and the existing "add a character" path as the last
resort.

---

## 4. Dead ends (so they aren't re-explored)

- **Linear-combination approach at 9 chars.** Cannot work — no vector satisfies `Σ|c|<25` at
  `n≤10`, so there is nothing to build stages from.
- **Near-budget linear-combination vectors (`Σ|c|≈26`).** A wrapped accept-area covers (almost)
  the whole ring and rejects ≈0 seeds — no constraint. The 11-char `Σ|c|=24` borderline vectors
  were worse than useless: numerical wrap _excluded the true seed_.
- **Precomputed prefix→seed tables.** `25⁹ ≈ 3.8e12` entries — not shippable. Indexing only the
  first few characters does not subdivide cleanly (samples are 2 LCG steps apart with different
  multipliers). The baked artifact should be the small reduced lattice basis, not a lookup table.

---

## 5. Implementation summary

The direct CVP reconstruction is the shipped first-search algorithm: 9 characters, no residual
scan, small baked table, fast. Key implementation points:

- **[`charrss.py`](charrss.py)** — [`cvp_basis`](charrss.py#L114) / [`cvp_prepare`](charrss.py#L146) / [`cvp_search`](charrss.py#L165) are the canonical
  reconstruction. The shipped runtime uses Schnorr-Euchner enumeration with a
  regenerate-and-verify at each leaf, making rare single-Babai near-edge misses a non-issue
  (5000/5000, no fallback).
- **[`tools/gen_charrss_constants.py`](tools/gen_charrss_constants.py)** — bakes the basis + Gram-Schmidt into
  [`docs/js/charrss_constants.js`](docs/js/charrss_constants.js) behind a self-test gate.
- **[`tools/charrss_difftest.mjs`](tools/charrss_difftest.mjs)** — differential-tests the JS port against [`docs/js/charrss.js`](docs/js/charrss.js).

### One-paragraph summary

The character RSS problem is truncated-LCG state recovery: each observed character leaks
~4.64 bits of the 32-bit anchor seed. Solving it directly with a single Babai closest-vector
computation against an LLL-reduced HNP lattice needs no linear-combination budget, uses a tiny
~9-dimensional lattice, and — as measured — recovers the exact seed from **9 characters,
5000/5000, with no brute-force residual, in ~0.26 ms**.
